wie der API funktionniert : 
So funktioniert eure API jetzt und so können Unternehmen sie nutzen:

**1. Grundprinzip**
- Eure Plattform ist die externe Punkte-Logik-Engine.
- Jedes Unternehmen bekommt einen eigenen Tenant mit eigener Punkte-Ratio und eigenem API-Key.
- Alle Punktebewegungen werden als Historie gespeichert und für Analytics genutzt.

**2. Onboarding für ein neues Unternehmen**
1. Unternehmen ruft POST /api/v1/organizations/register auf.
2. Antwort enthält:
- organization.id
- pointsRatio
- apiKey (nur bei Erstellung sichtbar)
3. Unternehmen speichert den apiKey sicher im eigenen Backend/Secret-Store.
4. Für alle weiteren API-Calls werden organizationId und Header x-api-key verwendet.

**3. Operativer Einsatz im Shop oder in der App**
- Beim Kauf:
POST /api/v1/points/earn
Eingaben: organizationId, externalCustomerId, amountEur, optional metadata  
Ergebnis: Punkte werden mit Ratio berechnet und gutgeschrieben.  
Wichtig: Profil wird automatisch erstellt, wenn es noch nicht existiert.

- Beim Einlösen einer Belohnung:
POST /api/v1/points/redeem
Eingaben: organizationId, externalCustomerId, points, optional metadata  
Ergebnis:
- Erfolg: Punkte werden abgezogen
- Nicht genug Punkte: Status 409 mit Ablehnungsgrund

- Für Dashboard und Reporting:
GET /api/v1/analytics/overview?organizationId=...
Ergebnis:
- Kundenanzahl
- Gesamtumsatz
- Punkte-Historie pro Tag (earn/redeem)
- letzte Transaktionen

- Für Business-Regeln:
PATCH /api/v1/organizations/{organizationId}/ratio
Ergebnis: neue Ratio aktiv für alle zukünftigen Earn-Transaktionen.

**4. Sicherheit**
- Auth über x-api-key pro Organisation.
- In der Datenbank wird nur der Hash des API-Keys gespeichert.
- Service-Role-Key bleibt ausschließlich serverseitig in eurer Plattform.
- Unternehmen sollten eure API nur aus ihrem Backend aufrufen, nicht direkt aus dem Frontend.

**5. Typischer Integrationsfluss bei Unternehmen**
1. Einmalig Tenant registrieren.
2. API-Key im Secret Manager speichern.
3. Nach jedem Checkout Earn-Endpoint aufrufen.
4. Vor Reward-Freischaltung Redeem-Endpoint aufrufen.
5. Für interne Auswertungen regelmäßig Analytics abrufen.

**6. Fertige Doku/Collections in eurem Repo**
- OpenAPI-Spezifikation: openapi.yaml
- Postman Collection: loyalty-engine.postman_collection.json
- Insomnia Collection: loyalty-engine.insomnia.json
- Technische Übersicht: README.md

Die Rollen sind in der `memberships`-Tabelle definiert, nicht direkt im Supabase-Auth-User.

Kurz gesagt:

1. **Rollenmodell**
- Tabelle: 20260410_memberships.sql
- Spalten:
  - `user_id` (Supabase Auth User)
  - `organization_id`
  - `role`
- Erlaubte Rollen per DB-Constraint:
  - `admin`
  - `member`

Technisch ist das über:
- `check (role in ('admin', 'member'))`
abgesichert.

2. **Wie Rolle gesetzt wird**
- Beim Erstellen einer neuen Organization in route.ts:
  - Wenn ein User eingeloggt ist, wird automatisch eine Membership mit Rolle `admin` angelegt.
- Das passiert über:
  - user-membership.ts (`assignAdminMembership`)

3. **Wie Rolle ausgewertet wird**
- Für Dashboard-Endpunkte wird erst der aktuelle eingeloggte User aufgelöst und seine Membership geladen:
  - user-membership.ts (`getCurrentMembershipContext`)
- Daraus kommen:
  - `organizationId`
  - `role`

4. **Wo Rolle Rechte steuert**
- Ratio-Update im Dashboard ist admin-only:
  - route.ts
  - Prüft explizit: `membership.role !== 'admin'` -> Forbidden (403)

5. **Datenisolation pro Organization**
- Zusätzlich zu App-Checks gibt es RLS-Policies in der Migration:
  - Nur Membership-User sehen Daten ihrer `organization_id`
  - Gilt für `organizations`, `customer_profiles`, `points_transactions`, `memberships`

Wenn du willst, kann ich dir jetzt noch ein kleines Admin-Endpunkt-Set bauen (`/api/v1/dashboard/memberships`) zum Einladen von Teammitgliedern und Rollenwechsel `member <-> admin`.

Perfekt, genau so testest du die normale User-Ansicht:

1. Erstelle einen zweiten Account (Landing: Registrieren).
2. Weisen diesem Account in Supabase die Rolle member zu (gleiche Organization wie dein Admin-User).
3. Melde dich mit diesem zweiten Account im Dashboard an (am besten im Inkognito-Fenster).

SQL (Supabase SQL Editor) dafür:

```sql
-- 1) User IDs prüfen
select id, email from auth.users order by created_at desc;

-- 2) Organizations prüfen
select id, name from public.organizations;

-- 3) Membership als member setzen (oder updaten)
insert into public.memberships (user_id, organization_id, role)
values ('USER_ID_HIER', 'ORG_ID_HIER', 'member')
on conflict (user_id, organization_id)
do update set role = 'member';
```

Alternative (mit deinem jetzigen Account testen):
```sql
update public.memberships
set role = 'member'
where user_id = 'DEIN_USER_ID';
```
Dann siehst du sofort die Member-Rechte, aber du bist temporär kein Admin mehr.
